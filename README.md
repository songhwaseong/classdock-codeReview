**`index.html` 을 브라우저로 열면 바로 뜹니다** — 서버도 빌드도 인터넷도 필요 없습니다.

## 다시 만들기

소스를 고친 뒤 리뷰 페이지에 반영하려면:

```bash
MN_ROOT=D:/my/myOffice node generate-review-data.mjs
```

`MN_ROOT` 은 **`scripts.manifest.json` 이 들어 있는 폴더**를 가리켜야 합니다 — 그 파일이 있는지로
소스 루트를 판정하기 때문입니다. 지정하지 않으면 부모 폴더 → 형제 폴더 `ClassDock` 순으로 찾아보고,
거기에도 없으면 확인한 위치를 찍고 멈춥니다.

이 리뷰 폴더는 소스 레포 밖에 있어 자동 탐색에 걸리지 않으므로 `MN_ROOT` 지정이 반드시 필요합니다.
위 경로는 이 체크아웃 기준이며(`D:\my\code-review` 옆의 `D:\my\myOffice`), 소스를 다른 곳에 두었다면
그 경로로 바꿔 주세요.

PowerShell 에서는:

```bash
$env:MN_ROOT="D:\my\myOffice"; node generate-review-data.mjs
```

## 설계 메모

- **다이어그램은 손으로 그리지 않았습니다.** 계층도·의존 그래프·공개 API 경계도는
  `scripts.manifest.json` 을 읽어 생성 시점에 SVG 로 만듭니다. manifest 가 바뀌면
  다이어그램도 따라 바뀌므로 그림이 코드와 어긋나지 않습니다.
- **CDN 의존 0.** 원본 앱이 오프라인 우선이라 리뷰 산출물도 같은 원칙을 지켰습니다.
  Mermaid 같은 런타임 렌더러도, 웹폰트도 쓰지 않습니다.
- **구간은 경계가 있을 때만.** `desktop/launcher.cs`(9천 줄대)는 기능별 구간으로 잘라 실었고,
  줄 번호는 원본 기준 그대로입니다. 화면에도 `L786–L899 / 전체 8,651줄` 처럼 그때 잰 값으로 표시됩니다.
  줄 수는 화면에서 생성 시점 값으로 보여 주고, 리뷰 문장에는 적지 않습니다 — 소스가 자라면
  문장만 조용히 낡기 때문입니다(같은 이유로 산출물 크기도 생성 때 직접 잽니다).
  꼭 문장에 숫자가 필요하면 생성 때 재서 끼워 넣습니다. 재는 함수는 `lib/source-metrics.mjs` 에
  모아 두었습니다 — `spreadsheet-viewer.js` 의 "renderXlsx 하나가 파일의 73%", `map-viewer.js` 의
  "mountMapEditor 가 파일의 47%", `db-client.js` 의 "mount 가 파일의 78%", 개요의 "가장 큰 파일 넷",
  "가장 큰 단위 테스트 셋", `src/js` 전체 줄 수, 테스트 개수·줄 수, `core.js`·`state.js` 의
  줄 수가 모두 손으로 적은 값이 아니라 매번 세는 값입니다. 앞서 이 자리에 하드코딩돼 있던
  "5,915줄 / 앞 4,000줄만" 이 수식 엔진 분리 후에도 남아 있었고, 그 뒤 `core.js` 4,104 ·
  `code-viewer.js` 4,034 · `state.js` 646 도 같은 식으로 어긋난 것이 이 규칙을 넓히고 도우미를
  한곳으로 모은 이유입니다. 2026-09-03 갱신에서도 세 군데가 같은 식으로 낡아 있었습니다 —
  "브라우저 쪽 558줄"(실제 1,324줄), "전역 스크립트로 6만 줄"(실제 118,000줄),
  "core.test.js 가 가장 큰 단위 테스트"(실제 3위). 셋 다 재는 값으로 바꿨습니다.
- **구간 분할은 함수 경계가 있을 때만.** `spreadsheet-viewer.js` 는 1,372줄부터 끝까지가
  `renderXlsx` 한 함수, `map-viewer.js` 는 뒤쪽 절반이 `mountMapEditor` 한 함수라 구간을 어디로
  잡아도 함수 중간이 잘립니다. 그래서 두 파일은 상한을 올려 통째로 싣습니다. 구간은 최상위 선언이
  여럿인 `launcher.cs` 처럼 자연스러운 경계가 있을 때만 씁니다.
- **구간도 줄 번호로 적지 않습니다.** `launcher.cs` 의 구간 31개는 `[시작줄, 끝줄]` 이 아니라
  코드 안의 문자열(함수 이름·라우팅 경로)을 앵커로 두고 생성 때 다시 찾습니다. 앞서 줄 번호로
  적어 두었더니 `launcher.cs` 가 7,118 → 7,861줄이 되는 사이 **구간 전부가 어긋나** "인증 판정"을
  눌러도 폴더 고르기 코드가 뜨는 상태였습니다. 화면상으로는 코드가 잘 뜨기 때문에 눈으로는
  드러나지 않는 종류의 낡음이라, 앵커를 못 찾으면 생성 스크립트가 경고하게 해 두었습니다.
- **곁다리 파일의 자리도 앵커로 적습니다.** `review-comments.js` 의 지목 주석, `flows.js` 의 흐름
  단계, `contracts.js` 의 계약 카드도 오랫동안 `line: 2478` 처럼 숫자를 적어 두었고 이쪽에는
  아무 검사가 없었습니다. 2026-08-22 에 세어 보니 227곳 중 **47곳이 어긋나 있었고 3곳은 빈 줄을,
  15곳은 어느 구간에도 실리지 않은 줄을** 가리키고 있었습니다. 일부는 소스가 자라며 밀린 것이지만
  일부는 훨씬 전부터 엉뚱한 코드를 가리켰습니다 — "임의 Python 실행의 입구" 가 지도 검색 키
  라우팅을, "npm 250MB 상한" 이 런처가 아니라 `npm_package_runner.js` 에 있는 검사를 가리켰습니다.
  구간이 겪은 것과 똑같은 낡음이라 같은 처방을 썼습니다:

  ```js
  { file: 'desktop/launcher.cs', at: 'string json = RunPython(body);' }
  { file: 'src/js/lazy.js',      at: 'const BUNDLES = {', below: 2 }
  ```

  들여쓰기가 바뀌어도 살아남게 **트림 비교**만 하고, 같은 줄이 여럿이면 고르지 않고 경고합니다
  (`nth` 로 명시할 수 있습니다). 브레이스 한 줄처럼 또렷하지 않은 자리는 위쪽의 유일한 줄을
  앵커로 잡고 `below` 로 내려갑니다 — 193곳을 옮기면서 `nth` 가 필요한 자리는 하나도 없었습니다.
  생성 스크립트가 줄 번호로 바꿔 `lineAnchors` 표에 담고, `app.js` 가 그 표로 자리를 찾습니다.
  파일 첫 줄처럼 앵커가 필요 없는 34곳은 숫자를 그대로 둡니다.
- **그리고 세 가지를 경고합니다.** 앵커를 못 찾은 것(코드가 바뀜), 같은 줄이 여럿이라 고를 수 없는
  것, 그리고 **찾긴 했지만 어느 섹션에도 실리지 않아 눌러도 아무 일이 없는 것**. 마지막 검사가
  없던 동안 15곳이 죽은 채로 있었고, 엔드포인트 대조는 통과하고 있었습니다 — 계약이 가리키는
  코드가 화면에 없는 것은 그 검사가 보지 않는 종류의 빈틈이었기 때문입니다.
- **상한은 최대 파일이 아니라 성장 속도에 맞춥니다.** `MAX_LINES` 를 "최대 파일 + 8%"(5,600)로
  잡았을 때, 정작 상한에 다가온 것은 최대 파일이 아니라 한 주 만에 2,785 → 4,930줄이 된
  `whiteboard.js` 였습니다. 상한에 부딪히는 것은 대개 "지금 가장 큰 파일"이 아니라 "지금 가장 빨리
  자라는 파일"입니다. 그 뒤 7,000 으로 올렸더니 이번에는 `map-viewer.js` 가 9일 만에 4,809 → 6,541줄로
  자라 여유를 458줄만 남기고 다가왔습니다 — 90% 알림이 실제로 먼저 떴습니다. 지금은 9,500 으로
  두었지만, 상한을 올리는 것은 미루는 조치일 뿐입니다.
- **정합성은 생성 시 검사.** 섹션 id 중복, 빈 요약, 읽지 못한 파일, 섹션에 실리지 않은
  `src/js` 파일과 `docs` 문서, 계약 카드가 없는 전역 공개 API, 상한을 넘겨 꼬리가 잘린 파일,
  상한의 90% 를 넘긴 파일, 찾지 못한 구간 앵커, 찾지 못하거나 여럿과 일치하는 곁다리 앵커,
  어느 섹션에도 실리지 않은 줄을 가리키는 파일 위치를 생성 스크립트가 경고합니다. 소스에 새 설계
  문서가 생기거나 파일이 자라 리뷰에서 일부가 빠지면 다음 생성 때 드러납니다.
- **EXE 엔드포인트도 대조합니다.** 전역 공개 API 는 `manifest` 의 `moduleBoundaries` 라는 정답
  목록이 있지만 EXE 엔드포인트에는 그런 목록이 없어서, `launcher.cs` 의 라우팅 사슬 자체를
  목록으로 삼습니다. 계약 카드마다 `endpoints` 를 적어 두고 양쪽으로 맞춰 봅니다 — 런처에
  있는데 아무 카드도 안 맡은 경로, 카드가 적었는데 런처에 없는 경로, 두 카드가 겹쳐 맡은 경로를
  각각 경고합니다. 이 검사가 없던 동안 지도 엔드포인트 10개가 조용히 빠져 있었고, 파일·문서
  커버리지 검사는 전부 통과하고 있었습니다. 지금은 매번 `140/140` 처럼 비율을 찍습니다 —
  2026-08-31 에는 환율 4개와 SSH 파일 올리기·개인키 고르기 7개, 모두 11개가 이 검사로 드러났습니다.
  2026-09-03 에는 DB 클라이언트 19개·진단 5개·원격 파일 3개, 모두 27개가 한꺼번에 드러났습니다.
- **테스트는 전수가 아니라 표본.** 단위 110/136 · E2E 26/59 를 싣습니다. 기능별 대표를 고른
  것이라 미참조 테스트는 경고 대상이 아니고, 대신 생성 스크립트가 매번 이 비율을 찍습니다.
- **용어 사전도 검사 대상.** `sections/05-glossary.mjs` 의 100개 항목은 짐작이 아니라 리뷰 산문의
  어휘 빈도로 골랐습니다(전역 850회, 계층 169회, 폴백 68회 …). 사전에는 있는데 리뷰 본문에는
  더 이상 나오지 않는 말이 생기면 생성 스크립트가 경고하므로, 문장을 고치는 동안 사전이 조용히
  낡지 않습니다.
- **다만 반대 방향은 자동으로 못 잡습니다.** "리뷰에 새로 자주 나오게 됐는데 사전에 없는 말"은
  빈도만으로 가려지지 않습니다 — 세어 보면 파일(645)·실행(295)·저장(233) 같은 평범한 한국어가
  상위를 채우고, 정작 넣어야 할 타일(20)·지오코딩(2)은 한참 아래에 묻힙니다. "자주 나오는 말"과
  "설명이 필요한 말"이 다르기 때문입니다. 그래서 낱말을 맞히려 들지 않고 **"다시 훑을 때가 됐다"는
  신호만** 남깁니다 — `CURATED` 에 마지막으로 훑은 시점의 산문 규모와 주제 묶음을 적어 두고,
  산문이 10% 넘게 늘거나 새 묶음(예: `지도`)이 생기면 알립니다. 지도가 통째로 들어왔을 때
  아무 신호도 없었던 것이 이 장치를 둔 이유입니다. 2026-08-22 에 연대표·원격 터미널이 들어왔을
  때는 두 신호(새 묶음 2개 · 산문 +12%)가 모두 떴고, 그 뒤 사전에 SSH · PTY·ConPTY ·
